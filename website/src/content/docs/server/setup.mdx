The `@chatcops/server` package provides a universal chat handler that works with any HTTP framework via adapters.

## Installation

```bash
npm install @chatcops/server
```

## Configuration

```typescript
import { chatcopsMiddleware } from '@chatcops/server';
import { FAQKnowledgeSource, LeadCaptureTool } from '@chatcops/core';
import type { LeadData } from '@chatcops/core';
import { postgresStorage } from '@chatcops/store-postgres';
import pg from 'pg';

const saveLead = async (_lead: LeadData) => {};
const myStore = postgresStorage({ db: new pg.Pool({ connectionString: process.env.DATABASE_URL }) });

const handler = chatcopsMiddleware({
  // Required: AI provider
  provider: {
    type: 'claude',                      // 'claude' | 'openai' | 'gemini'
    apiKey: process.env.ANTHROPIC_API_KEY!,
    model: 'claude-haiku-5-5',  // Optional, each provider has defaults
  },

  // Required: System prompt
  systemPrompt: `You are a helpful customer support assistant.
    Be friendly, concise, and helpful.
    If the user provides contact info, use the lead capture tool.`,

  // Required, or allowAnonymous: true: signs the session tokens the widget fetches
  sessionSecrets: [process.env.CHATCOPS_SESSION_SECRET!],

  // Optional: Tools
  tools: [
    new LeadCaptureTool((lead) => saveLead(lead)),
  ],

  // Optional: Tool execution timeout in ms (default: 30000)
  toolTimeoutMs: 30_000,

  // Optional: Most tokens in one reply (default: 4096)
  maxTokens: 1024,

  // Optional: Sampling temperature (default: the provider's own). Claude ignores it.
  // The allowed range depends on the provider.
  temperature: 0.7,

  // Optional: Knowledge base
  knowledge: [
    new FAQKnowledgeSource([
      { question: 'What are your hours?', answer: 'We are open 9am-5pm EST.' },
    ]),
  ],

  // Optional: Rate limiting per visitor IP, a sliding window. Counted in
  // `storage` when it has counters, so the limit holds across instances.
  rateLimit: {
    maxRequests: 30,     // Max requests per window
    windowMs: 60_000,    // Window duration in ms
  },

  // Optional: Webhooks
  webhooks: [
    {
      url: 'https://hooks.example.com/chatcops',
      events: ['lead:captured'],
      secret: process.env.WEBHOOK_SECRET,
    },
  ],

  // Optional: Analytics
  analytics: true,

  // Optional: Persistent storage. See /server/storage.
  storage: myStore,

  // Optional: the sites that can use the chat (see Allowed origins below)
  allowedOrigins: ['https://acme.com', 'https://*.acme.com'],
});
```

## ChatCopsServerConfig

```typescript
import type { AIProvider, Budgets, ChatCopsStorage, ChatTool, ConversationStore, KnowledgeSource, LocaleStrings, Logger, WebhookConfig } from '@chatcops/core';

interface ChatCopsServerConfig {
  // A config (see Providers for every option), or a provider object.
  provider:
    | { type: 'claude' | 'openai' | 'gemini'; apiKey: string; model?: string }
    | AIProvider;
  systemPrompt: string;
  tools?: ChatTool[];
  toolTimeoutMs?: number;
  maxTokens?: number;
  temperature?: number;
  knowledge?: KnowledgeSource[];
  budgets?: Budgets | false;   // on by default, see Budgets below
  preChatFields?: string[];   // pre-chat form fields to keep; kept from the first message on
  rateLimit?: {
    maxRequests: number;
    windowMs: number;
  };
  webhooks?: WebhookConfig[];
  analytics?: boolean;
  storage?: ChatCopsStorage;            // where conversations, counters and locks live
  retention?: { conversationsDays?: number };   // for purge(); default 30
  allowedOrigins?: string[];   // default ['*']
  clientIp?: (request: Request) => string | null | undefined;   // fetch handlers, see the fetch runtimes page
  sessionSecrets?: string[];   // turns on session tokens, see Session tokens below
  sessionTtlSec?: number;      // default 900
  allowAnonymous?: boolean;    // accept chat without a session token; default false
  turnstile?: { secretKey: string; action?: string; expectedHostnames?: string[]; timeoutMs?: number };
  identity?: { secret: string; tiers?: Record<string, Budgets> };   // signed-in visitors, see below
  exposeUsage?: boolean;   // token usage in protocol v1 finish parts; default false
  logger?: Logger;         // where notes and errors go, see Logging below; default consoleLogger()
  /** @deprecated Ignored by the server. Use the widget's `strings` option. */
  i18n?: {
    defaultLocale: string;
    locales: Record<string, LocaleStrings>;
  };
}
```

### A provider object instead of a config

`provider` also takes an object you built yourself: anything with `step()` or `chat()` (the [AIProvider interface](/core/providers/#aiprovider-interface)). Use it for a provider ChatCops doesn't have, or in tests with `scriptedProvider()`, which plays back a script instead of calling a model:

```typescript
import { createChatHandler } from '@chatcops/server';
import { scriptedProvider, textStep } from '@chatcops/core/testing/provider';

const handler = createChatHandler({
  provider: scriptedProvider([textStep('Hello from a test.')]),
  systemPrompt: 'Be brief.',
});
```

## Storage

By default everything lives in memory, per process. That's fine on one long-running server, but on Vercel, Lambda or Workers each instance has its own memory, so the server logs a warning there. Pass a store package as `storage`:

```typescript
import { chatcopsMiddleware } from '@chatcops/server';
import pg from 'pg';
import { postgresStorage } from '@chatcops/store-postgres';

const handler = chatcopsMiddleware({
  provider: { type: 'claude', apiKey: process.env.ANTHROPIC_API_KEY! },
  systemPrompt: 'You are a helpful assistant.',
  storage: postgresStorage({ db: new pg.Pool({ connectionString: process.env.DATABASE_URL }) }),
});
```

With a storage that has key-value support, the rule that only one reply is written per conversation at a time holds across all your server instances, not just within one.

Nothing is deleted on its own. The handler's `purge()` deletes conversations last updated more than `retention.conversationsDays` (default 30) days ago. Call it on a schedule, from a cron job or a Workers cron trigger:

```typescript
import { createChatHandler } from '@chatcops/server';

const { purge } = createChatHandler({
  provider: { type: 'claude', apiKey: process.env.ANTHROPIC_API_KEY! },
  systemPrompt: 'Be helpful.',
});
await purge(); // resolves how many were deleted
```

## Allowed origins

`allowedOrigins` lists the sites whose pages can use the chat. Each entry is an exact origin, or a wildcard for subdomains:

```typescript
import type { ChatCopsServerConfig } from '@chatcops/server';

const config: Partial<ChatCopsServerConfig> = {
  allowedOrigins: ['https://acme.com', 'https://*.acme.com'],
};
```

A browser request from any other page gets `403 {"error":"origin_not_allowed"}` before the model is called, and the server logs the origin it refused. Without the list (or with `['*']`), any site can put your chat on its pages and spend your tokens. Set it in production.

Entries need the scheme and no path: `https://acme.com`, not `acme.com` or `https://acme.com/`. `https://*.acme.com` matches `https://docs.acme.com` but not `https://acme.com` itself, so list both if you need both. Include the port when it isn't the default, as in `http://localhost:4321`.

Requests without an `Origin` header, such as `curl` or a call from your own server, still go through. The list stops other sites embedding your bot. It doesn't stop scripts, which can send any `Origin` they like. Rate limits and budgets are what stop those.

`cors` is the older option for one origin. It still works as a one-item `allowedOrigins`, with a deprecation warning.

## Session tokens

Without session tokens, anyone who knows a conversation id can keep talking in that conversation, and the model answers with its history in view. Ids are random, so this is about leaked ids and guessing. So from 1.0 the chat needs a short-lived token that's bound to one conversation and one site, signed with `sessionSecrets`:

```typescript
import type { ChatCopsServerConfig } from '@chatcops/server';

const config: Partial<ChatCopsServerConfig> = {
  sessionSecrets: [process.env.CHATCOPS_SESSION_SECRET!],
};
```

Each secret needs at least 32 bytes; `openssl rand -base64 32` makes one. Keep it on the server, never in a `NEXT_PUBLIC_` or `VITE_` variable. The server refuses to start with a shorter one.

The client asks for a token at the chat URL plus `/session` (`/api/chat/session` for a chat at `/api/chat`):

```
POST /api/chat/session
{ "conversationId": "c_8f2", "previousToken": "eyJ..." }

200 { "token": "eyJ...", "expiresAt": 1792411200000, "conversationId": "c_8f2" }
```

Then it sends `Authorization: Bearer <token>` with each chat request. Tokens last `sessionTtlSec` (15 minutes by default). To keep a conversation, the client sends its id with the token it had for it, which still works up to 30 days after it expired. An id that has nothing stored yet is given out as is, since there's nothing in it to read. An id that has messages, sent without its token or with a token for another conversation or site, gets a new conversation instead, so a guessed or leaked id is useless.

The widget does all of this on its own from 0.6. When a chat request gets a 401, it asks `/session` for a token, keeps it in `localStorage` and sends the request again. When the server answers with a new conversation id, the widget moves to it.

With Express, mount the middleware with `app.use('/api/chat', ...)` so `/api/chat/session` reaches it. On Vercel or Next.js, export the same handler from a second route file at `app/api/chat/session/route.ts`. A Cloudflare Worker gets every path already.

Chat requests without a token get `401 session_required`, an expired token gets `401 token_expired`, and a token for another conversation gets `401 conversation_mismatch`.

A server without `sessionSecrets` refuses to start unless it sets `allowAnonymous: true`, which accepts chat without tokens. Set it with `sessionSecrets` too while widgets before 0.6, which don't send tokens, are still around: requests without a token then go through, and the ones that send one are still checked. Set it alone for a server only you reach, such as a local test, or one behind your own login. Clients that don't fetch tokens, such as the AI SDK's `useChat`, need it as well (see [AI SDK](/server/ai-sdk/)). The short examples on other pages leave `sessionSecrets` out to keep to their point. Add it to yours.

To change the secret, put the new one first and keep the old one until its tokens have expired: `sessionSecrets: [newSecret, oldSecret]`. New tokens are signed with the first, and any of them verifies.

### Turnstile

A script can still ask for as many sessions as it likes. To make that harder, have `/session` check a [Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/) token first:

```typescript
import type { ChatCopsServerConfig } from '@chatcops/server';

const config: Partial<ChatCopsServerConfig> = {
  sessionSecrets: [process.env.CHATCOPS_SESSION_SECRET!],
  turnstile: { secretKey: process.env.TURNSTILE_SECRET_KEY! },
};
```

Then give the widget the site key, with `data-turnstile-site-key="0x4AAA..."` or `turnstileSiteKey` in `ChatCops.init()`. The widget loads Cloudflare's script only when it first needs a session, so visitors who never open the chat don't load it. The check is invisible for most visitors. When Cloudflare wants a click, the challenge shows near the bottom right corner of the page, outside the widget. A page with a Content Security Policy needs `https://challenges.cloudflare.com` in `script-src` and `frame-src`.

The server checks the token with Cloudflare, sending the visitor's IP, and refuses a missing or failed one with `401 turnstile_failed`. If Cloudflare can't be reached, `/session` answers `503` and issues nothing. A session refreshed with its previous token skips Turnstile, since it passed when it was first issued. `action`, `expectedHostnames` and `timeoutMs` (default 5000) are optional, and a client that retries `/session` with the same Turnstile token can send the same `idempotencyKey` (a UUID) each time.

### Signed-in visitors

When your site knows who the visitor is, it can tell the chat. Your server signs a short `userToken` for the signed-in user, and the widget sends it when it asks for a session:

```typescript
import type { ChatCopsServerConfig } from '@chatcops/server';

const config: Partial<ChatCopsServerConfig> = {
  identity: {
    secret: process.env.CHATCOPS_IDENTITY_SECRET!,   // at least 32 bytes, shared with your site's server
    tiers: { pro: { perConversation: { messages: 1000 } } },
  },
};
```

The token is an HS256 JWT with `sub` (the user id, up to 128 characters), `exp` in seconds, and optionally `tier`. Sign it on your server, never in the browser. With Node.js and no library:

```typescript
import { createHmac } from 'node:crypto';

function chatUserToken(userId: string, tier?: string): string {
  const encode = (value: object) => Buffer.from(JSON.stringify(value)).toString('base64url');
  const body = `${encode({ alg: 'HS256', typ: 'JWT' })}.${encode({ sub: userId, exp: Math.floor(Date.now() / 1000) + 86_400, tier })}`;
  return `${body}.${createHmac('sha256', process.env.CHATCOPS_IDENTITY_SECRET!).update(body).digest('base64url')}`;
}
```

Then put it on the page with `data-user-token="..."` on the script tag, or `userToken` in `ChatCops.init()`.

The user id goes into the session token and is stored on the conversation with its first message. The same user can resume that conversation later with a fresh token, even without the old session token. Another user, or an anonymous visitor, can't. A `tier` swaps in that tier's budgets (merged over `budgets`) for the user's replies. A `userToken` that doesn't verify or has expired gets `401 session_required`, rather than an anonymous session, so a bug on your site shows up. The widget sends the token every time it asks for a session, so give it a lifetime longer than a visit, such as a day.

## Budgets

Budgets cap what replies can cost, so a script hammering your endpoint can't run up the bill. They're counted in `storage`, so they hold across instances.

They're on by default:

| Scope | Default | Why |
|---|---|---|
| `perConversation` | 200 replies | The widget keeps a conversation across visits, so this counts replies rather than tokens, which would grow with the size of your system prompt. |
| `perIpPerDay` | 2M tokens | The cost backstop. A script can start new conversations at will, but not new IPs as easily. |
| `globalPerDay` | none | No single number fits every site. Set one. |

The server logs the budgets in force once at startup:

```
[chatcops] Budgets: 200 replies per conversation (default), 2M tokens per IP per day (default). No daily total is set; `budgets.globalPerDay` caps your whole bill. Set `budgets` to change them, or `budgets: false` to turn them off.
```

A scope you set replaces its default whole. `false` turns a scope off, and `budgets: false` turns them all off:

```typescript
import type { ChatCopsServerConfig } from '@chatcops/server';

const config: Partial<ChatCopsServerConfig> = {
  budgets: {
    perConversation: { tokens: 400_000 },            // over the conversation's lifetime
    perIpPerDay: { tokens: 2_000_000, messages: 200 },
    globalPerDay: { usd: 20 },                        // the backstop
    // What a request cost, for the dollar cap. Price cached input at its discount.
    price: (usage: { inputTokens: number; outputTokens: number }) => (usage.inputTokens * 1 + usage.outputTokens * 5) / 1_000_000,
  },
};
```

Tokens count input and output at face value, and every request sends the conversation so far, so a long conversation uses up a token budget faster than its length suggests. Budgets are checked before each model request and charged after it, so a reply can go over by one request, and each request asks for no more output than is left. A used-up budget ends the reply with an error instead of calling the model, and the server logs which one.

The per-IP budget needs the visitor's IP, so it's skipped for requests where the adapter can't tell.

For persistent conversations, custom stores, Postgres, Redis, and the storage capabilities available to the server, see [the storage page](/server/storage/).

## Webhooks

`lead:captured` is the only webhook event today. It's sent when the `capture_lead` tool saves a lead.

Each webhook gets a POST with a JSON body for every event it subscribes to:

```json
{
  "id": "evt_6f1c…",
  "type": "lead:captured",
  "created": 1792411200000,
  "data": { "lead": { "name": "Priya", "email": "priya@example.com" }, "conversationId": "c_123" }
}
```

`id` is the same on every retry, so use it to ignore duplicates; it's also in the `X-ChatCops-Event-Id` header.

**Retries.** A delivery is tried up to 3 times. Network errors, 429 and 5xx responses are retried (a 429's `Retry-After` is honored, up to 10 seconds); other 4xx responses are final, and redirects aren't followed. A delivery that fails for good is logged with the event type, id and the receiver's origin, never the body.

**Verifying the signature.** With a `secret`, each request has an `X-ChatCops-Signature: t=<unix seconds>,v1=<hex>` header, an HMAC-SHA256 of `<t>.<raw body>`. Verify it against the raw body, before parsing it:

```typescript
import express from 'express';
import { verifyWebhook } from '@chatcops/server';

const app = express();
app.post('/hooks/chatcops', express.text({ type: 'application/json' }), async (req, res) => {
  const valid = await verifyWebhook({
    body: req.body, // the raw string, not parsed JSON
    signature: req.get('X-ChatCops-Signature'),
    secret: process.env.WEBHOOK_SECRET!,
  });
  if (!valid) return res.status(400).end();

  const event = JSON.parse(req.body);
  // ...
  res.status(200).end();
});
```

`verifyWebhook` also rejects signatures older than 5 minutes (`toleranceSec` changes that).

**Allowed URLs.** Webhook URLs must use https, and hosts on loopback, private or link-local networks (`localhost`, `10.x`, `192.168.x`, `169.254.169.254` and so on) are refused when the server starts. For a receiver on your own machine during development, set `allowPrivateNetwork: true` on that webhook:

```typescript
import type { ChatCopsServerConfig } from '@chatcops/server';

const config: Partial<ChatCopsServerConfig> = {
  webhooks: [{ url: 'http://localhost:4000/hooks', events: ['lead:captured'], allowPrivateNetwork: true }],
};
```

## Logging

The server writes what it notices to a `Logger`: startup notes (budgets, security settings), refused requests, and every error it handles instead of throwing. Each line has a stable `event` name you can filter or alert on. By default the lines go to the console as `[chatcops] …`. For a log tool that parses JSON, use `jsonLogger()`, which writes one object per line to `console.error` (stderr on Node):

```typescript
import express from 'express';
import { jsonLogger } from '@chatcops/core';
import { chatcopsMiddleware } from '@chatcops/server';

const app = express();
app.post('/chat', chatcopsMiddleware({
  provider: { type: 'claude', apiKey: process.env.ANTHROPIC_API_KEY! },
  systemPrompt: 'You answer questions about Acme.',
  logger: jsonLogger({ level: 'warn' }),
}));
```

```json
{"time":"2026-10-28T14:02:11.420Z","level":"error","event":"tool_error","message":"Tool lookup_order threw","tool":"lookup_order","error":{"name":"Error","message":"connect ECONNREFUSED","stack":"…"}}
```

Or pass your own: anything with `debug`, `info`, `warn` and `error` methods that take `(event, message, fields)`, so pino, winston or a platform logger is a few lines of glue.

| Event | Level | When |
|---|---|---|
| `provider_error` | error | A reply failed at the model provider |
| `provider_setup_failed` | error | The provider couldn't start (a missing key, an unknown type) |
| `tool_error` | error | A tool threw. The full error is in `error`; see [Tools](/core/tools/#how-tools-work) for what the model sees |
| `lead_capture_failed` | error | The lead capture callback threw |
| `webhook_failed` | error | A webhook delivery failed after its retries |
| `unhandled_error` | error | Anything else that went wrong while answering a request |
| `analytics_write_failed`, `analytics_flush_failed` | error | Events couldn't be written to the store |
| `budget_exceeded` | warn | A budget is used up, so a reply was refused |
| `origin_refused` | warn | A page whose origin isn't in `allowedOrigins` was refused |
| `insecure_config` | warn, error | A security setting needs attention at startup |
| `reply_truncated`, `config_warning`, `memory_storage`, `client_ip`, `turnstile_unavailable` | warn | Something to fix in the setup |
| `budgets`, `security`, `legacy_stream_format` | info | Startup notes, and the first request in the 0.5 stream format |

## Request Schema

The server validates incoming requests with Zod:

```typescript
interface ChatRequest {
  conversationId: string,  // 1-128 chars
  message: string,         // 1-10000 chars
  messageId?: string,      // Optional, 1-128 chars
  protocol?: 1,            // Optional, asks for protocol v1 (see Response format)
  regenerate?: boolean | { assistantMessageId: string },  // Optional
  pageContext?: {           // Optional page context
    url: string,           // Valid URL (the prompt gets the first 2000 chars)
    title: string,         // Max 500 chars
    description?: string,  // Max 1000 chars
    contentSnippet?: string, // Max 2000 chars
    data?: { [key: string]: string },  // From the widget's setContext(): max 20 fields, keys 40 chars, values 500
  },
  locale?: string,         // Max 10 chars
  userData?: {              // Optional pre-chat data, max 50 fields
    [key: string]: string,  // Key max 100 chars, value max 500 chars
  },
}
```

The widget sends pre-chat answers in `userData`. See the [pre-chat form guide](/widget/pre-chat-form) for how the widget collects and submits these answers. Use the `preChatFields` option in [`ChatCopsServerConfig`](#chatcopsserverconfig) to limit which fields the server keeps.

## Response format

The server answers in one of two formats. The widget from 0.6 on sends `"protocol": 1` in the request body and gets protocol v1. Requests without it, from widgets before 0.6 or older custom clients, get the 0.5 format, which keeps working until 1.0. A client can also ask for v1 with an `x-chatcops-protocol: 1` header. The server logs one line the first time it answers in the 0.5 format, so you can tell when old widgets are still around. `chatcopsAiSdkHandler` answers in a third format, the AI SDK's, for apps built on `useChat` (see [AI SDK](/server/ai-sdk/)).

The server writes one reply per conversation at a time, so a second message sent while a reply is streaming is refused instead of answering the same history twice. The widget doesn't let visitors send while a reply streams, so this only shows up with custom clients.

Each reply is saved as one assistant message with its parts: the text, and every tool call and result in order. It's saved after each tool round, so a reply cut off partway still has the finished tool steps. A retry of a message that already has a finished reply gets that reply again, without calling the model.

### Protocol v1

Protocol v1 is the default stream format for modern ChatCops clients. Replies stream as typed Server-Sent Events (SSE) carrying granular event parts, with pre-stream refusals returned as JSON with standard HTTP error statuses.

For the full specification covering format negotiation, request fields, SSE framing, all 13 wire part variants, and HTTP error mappings, see the [Protocol Reference](/server/protocol/).

### The 0.5 format

Requests without `protocol` get plain chunks:

```
data: {"content":"Hello"}

data: {"content":" there"}

data: {"leadCaptured":true,"leadData":{"name":"Ada","email":"ada@example.com","projectDetails":"Support bot for an online store","source":"chatcops-widget"}}

data: {"done":true}

data: [DONE]
```

The stream can contain these chunks:

- `{"content":"..."}` for each text chunk.
- `{"leadCaptured":true,"leadData":{...}}` when the lead capture tool succeeds.
- `{"error":"rate_limit","retryAfter":12}` when the client is rate limited.
- `{"error":"provider_error"}` when the provider fails or can't be set up, when the model keeps calling tools past the limit, or when a reply is already being written for the same conversation.
- `{"error":"Invalid request","details":{...}}` when the request fails schema validation.
- `{"error":"internal_error"}` when the server hits an unexpected error.
- `{"done":true}` at the end of a successful reply.

Errors in this format are chunks in an HTTP 200 response, followed by `data: [DONE]`. A body that isn't JSON gets HTTP 400 `{"error":"Invalid JSON body"}`.
