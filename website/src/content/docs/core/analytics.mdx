title: Analytics

ChatCops includes a lightweight analytics collector that tracks conversation metrics server-side.

## Enabling Analytics

```typescript
import { chatcopsMiddleware } from '@chatcops/server';

chatcopsMiddleware({
  provider: { type: 'claude', apiKey: '...' },
  systemPrompt: '...',
  analytics: true,  // Enable analytics tracking
});
```

## Reading Stats with Express

`chatcopsAnalyticsHandler` returns the stats for the traffic handled by `chatcopsMiddleware`. Pass the **same config object** to both so they share one handler:

```typescript
import express from 'express';
import { chatcopsMiddleware, chatcopsAnalyticsHandler } from '@chatcops/server';

const config = {
  provider: { type: 'claude', apiKey: process.env.ANTHROPIC_API_KEY! },
  systemPrompt: 'You are a helpful assistant.',
  allowedOrigins: ['*'],
  analytics: true,
  analyticsToken: process.env.CHATCOPS_ANALYTICS_TOKEN,
};

const app = express();
app.use(express.json());

app.use('/chat', chatcopsMiddleware(config));
app.get('/analytics', chatcopsAnalyticsHandler(config));

app.listen(3001);
```

When `analyticsToken` is set, requests must include a bearer token:

```bash
curl -H "Authorization: Bearer <token>" http://localhost:3001/analytics
```

When unset, the endpoint is public and logs a warning the first time it is hit.

With a `storage` that has an event sink (`memoryStorage()`, Postgres, Redis, SQLite and Cloudflare stores all do), the server writes every event there too, and the endpoint counts from the store. Then the stats cover every server instance, not just the one answering. Pick the range with `from` and `to` in milliseconds. The default is the last 30 days:

```bash
curl -H "Authorization: Bearer <token>" "http://localhost:3001/analytics?from=1792368000000"
```

Without a store that can be queried, the stats come from the memory of the process that answers, which on serverless is one instance at a time. A range that isn't a number gets `400 {"error":"invalid_range"}`.

`GET /analytics` responds with the aggregated stats (or `null` if `analytics` is not enabled):

```json
{
  "totalConversations": 2,
  "totalMessages": 4,
  "leadsCaptured": 0,
  "averageMessagesPerConversation": 2,
  "eventCounts": { "conversation.started": 2, "message.sent": 2, "message.received": 2 }
}
```

## Tracked Events

When `analytics: true`, the server automatically tracks:

| Event | When |
|-------|------|
| `conversation.started` | New conversation ID first seen |
| `message.sent` | User sends a message |
| `message.received` | AI responds |
| `lead.captured` | Lead capture tool fires |

`ANALYTICS_EVENTS` from `@chatcops/core` has these names, so code doesn't have to spell them. Before 0.8 they were `conversation:started`, `message:sent`, `message:received` and `lead:captured`. Stats still count events a store saved under those names, so totals carry on across the upgrade, but `track()` and `getEvents()` treat them as names of your own. Webhook event names, such as `lead:captured` in a webhook's `events`, are separate and didn't change.

## AnalyticsCollector API

```typescript
import { AnalyticsCollector } from '@chatcops/core';

const analytics = new AnalyticsCollector();

// Track custom events
analytics.track('pricing.viewed', { plan: 'Team' });

// Get aggregated stats
const stats = analytics.getStats();
// {
//   totalConversations: 150,
//   totalMessages: 2340,
//   leadsCaptured: 23,
//   averageMessagesPerConversation: 15.6,
//   eventCounts: { 'conversation.started': 150, ... }
// }

// Get raw events (optionally filter by type)
const allEvents = analytics.getEvents();
const leads = analytics.getEvents('lead.captured');

// Clear all events
analytics.clear();
```

## AnalyticsStats Interface

```typescript
interface AnalyticsStats {
  totalConversations: number;
  totalMessages: number;
  leadsCaptured: number;
  averageMessagesPerConversation: number;
  eventCounts: Record<string, number>;
}

interface AnalyticsEvent {
  type: string;
  data?: Record<string, unknown>;
  timestamp: number;
}
```

## Storage

The built-in collector stores events in memory (max 1000 events). With `analytics: true` and a `storage`, the server already writes events to the store's sink, buffered and flushed as each reply ends. To do the same in your own code, use `BufferedEventSink`. It batches up to 50 events by default and flushes every 2 seconds. Call `flush()` when you need to wait for queued writes, such as before a process exits:

```typescript
import { BufferedEventSink, memoryStorage, statsFromSink } from '@chatcops/core';

const storage = memoryStorage();
const eventSink = storage.events;
if (!eventSink) throw new Error('Event storage is not configured');

const analytics = new BufferedEventSink(eventSink, {
  maxBatch: 50,
  flushMs: 2000,
});

analytics.track('pricing.viewed', { plan: 'Team' });
await analytics.flush();

const now = Date.now();
const stats = await statsFromSink(eventSink, {
  from: now - 24 * 60 * 60 * 1000,
  to: now,
});
```

Use a persistent `EventSink` implementation when events need to be shared across processes or survive restarts. Writes that fail are logged and dropped so analytics does not interrupt chat requests. `statsFromSink` requires the sink's optional `query` method; the range includes `from` and excludes `to`. It counts each `conversation:started` event as one conversation.

## Client-Side Events

Combine with widget events for full-stack analytics:

```typescript
// Client-side
declare const gtag: (command: 'event', eventName: string) => void;
ChatCops.on('open', () => gtag('event', 'chat_opened'));
ChatCops.on('message', (...args: unknown[]) => {
  const m = args[0] as { role: 'user' | 'assistant' };
  if (m.role === 'user') gtag('event', 'chat_message_sent');
});

// Server-side (automatic with analytics: true)
// conversation.started, message.sent, message.received, lead.captured
```
