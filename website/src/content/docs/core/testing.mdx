---
title: Testing your bot
description: Write conversations your bot should handle in YAML, and check them with chatcops test before you ship a prompt or model change.
---

A change to the system prompt, the model or the knowledge base can quietly break an answer that used to be right. `chatcops test` catches that. You write the conversations your bot has to get right in YAML, say what each reply should contain, and the command runs them against your bot and tells you which ones broke.

```bash
npx chatcops test
```

It exits 0 when every test passed, 1 when some failed, and 2 when it couldn't run (a bad eval file, a missing config), so it works as a CI step.

## The config

`chatcops test` reads the `server` section of `chatcops.config.ts`. It's the same config you give the server: the provider, system prompt, tools and knowledge.

```ts
import { LeadCaptureTool } from '@chatcops/core';
import { defineConfig } from '@chatcops/cli';

export default defineConfig({
  server: {
    provider: { type: 'claude', apiKey: process.env.ANTHROPIC_API_KEY! },
    systemPrompt: 'You answer questions about Acme plans and orders.',
    tools: [new LeadCaptureTool()],
  },
});
```

Tests run in process, through the same request path the server uses, so knowledge, tools, page context and locale all work as they do in production. Each test starts with fresh in-memory storage; your real conversation store is never touched.

## Eval files

By default the command runs every `evals/**/*.chat.yaml` file. Pass globs to pick others:

```bash
npx chatcops test "evals/pricing/*.chat.yaml"
```

An eval file has a name and a list of tests. Each test is one conversation, a turn at a time:

```yaml
version: 1
name: Pricing
tests:
  - name: quotes the Team price
    tags: [pricing]
    turns:
      - user: How much is the Team plan?
        expect:
          - contains: "$19"
          - not-contains: "$29"

  - name: remembers the plan on a follow-up
    turns:
      - user: Tell me about the Team plan.
      - user: How much is it per year?
        expect:
          - contains: "$190"
```

Each assertion has one key. `contains` takes a string or a list of strings that must all appear in the reply, and every assertion also works with a `not-` prefix to say the opposite. An assertion name that doesn't exist fails the whole run before anything is sent, so a typo can't make a test pass by checking nothing.

A test can also set:

- `pageContext`: the page the visitor is on (`url`, `title`, and optionally `description` and `contentSnippet`)
- `locale` and `userData`, as the widget would send them
- `mocks.tools`: a fixed result for a server tool, so the test doesn't place a real order or send a real email
- `repeat` and `passRate`: run the test several times and pass when that share of runs passed (models aren't deterministic)

`defaults` at the top of the file applies to every test in it. A test's own values win, and tool mocks are merged:

```yaml
version: 1
name: Orders
defaults:
  pageContext: { url: "https://acme.com/account", title: "Your account" }
  mocks:
    tools:
      lookup_order: { success: true, data: { status: "shipped" } }
tests:
  - name: says where the order is
    repeat: 5
    passRate: 0.8
    turns:
      - user: Where is order A-1001?
        expect:
          - contains: shipped
```

A mock for a tool your config doesn't have is an error, so a renamed tool can't leave a mock behind that no longer does anything.

Eval files can also be modules (`.chat.ts`, `.chat.mjs`) that export the same object as their default, when you'd rather build tests in code.

## Options

| Option | What it does |
| --- | --- |
| `[files...]` | Globs of eval files. Default `evals/**/*.chat.yaml`. |
| `--filter <text>` | Only tests whose name contains the text, or `tag:<name>` for a tag |
| `--repeat <n>` | Run every test n times, instead of each test's own `repeat` |
| `--concurrency <n>` | Tests run at once. Default 4. |
| `--reporter <name>` | `pretty` (the default) or `json`, which prints one JSON object with every turn's reply, tool calls, sources and token usage. Repeatable. |
| `--json` | The same as `--reporter json` |
| `--config <file>` | A config file other than `chatcops.config.*` in the current folder |

A failed test prints the reason for each failed assertion and the reply it checked:

```text
✗ evals/pricing.chat.yaml > quotes the Team price
    turn 1: the reply doesn't contain "$19"
    reply: The Team plan is $29 a month, billed monthly.

1 passed, 1 failed.
```

## Recorded replays

Running tests calls your model for real, which costs tokens and needs the API key. For CI, record the calls once and replay them:

```bash
npx chatcops test --record   # calls the APIs and saves what they answer
npx chatcops test --replay   # answers every call from the recordings
```

`--record` saves each eval file's calls next to it, in `__cassettes__/<file>.jsonl` (so `evals/pricing.chat.yaml` records to `evals/__cassettes__/pricing.chat.jsonl`). It records every HTTP call a test makes: the model, embedding calls for knowledge search, and tools that call APIs without a mock. Commit the folder with your eval files.

When the `CI` environment variable is set, as it is on GitHub Actions and most CI services, `chatcops test` replays by default, so CI needs no API keys and costs nothing. A provider config without an `apiKey` gets a stand-in key during replay, since nothing is sent. Keep the config file loading when a key is missing: read `process.env.ANTHROPIC_API_KEY` as it is, and don't throw at load time. `--live` calls the APIs anyway.

Each call is matched by its method, URL and body within its test. Any change that changes what gets sent fails the test instead of passing on an old answer:

- a new word in the system prompt
- another model
- a tool added or removed
- a new knowledge page in the context

The message says where the request changed:

```text
✗ evals/pricing.chat.yaml > quotes the Team price
    A call changed since it was recorded (POST https://api.anthropic.com/v1/messages, at system[0].text). Run chatcops test --record to record it again.
```

Run `--record` again after a change like that, check that the tests still pass, and commit the new recordings. `--record --filter` updates only the tests it ran, and recordings of tests you deleted are dropped the next time the file is recorded.

A few things to know about recordings:

- Headers aren't saved, and neither are query parameters like `key` or `api_key`. API keys usually travel in one of those, so they stay out of the files. The request and response bodies are saved, which means your system prompt and the replies are in the files, so treat them like the rest of your code.
- `repeat` records every run, and replay plays them back in the same order.
- Replays answer at once, so `latency` in a replayed run is not the real latency.

### GitHub Actions

```yaml
name: Evals
on: [pull_request]
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx chatcops test
```
