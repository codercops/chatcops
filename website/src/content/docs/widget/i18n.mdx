---
title: Internationalization
description: Localize the ChatCops widget for different languages.
---

The widget's own text is English by default. Translations ship as one small file per language, loaded only by sites that use that language, and you can override any string with `strings`. Languages are being added one at a time in [#55](https://github.com/codercops/chatcops/issues/55).

## Setting a Locale

The widget sends `locale` with every message, and the server asks the model to reply in that language.

### Via script tag

```html
<script
  src="https://cdn.jsdelivr.net/npm/@chatcops/widget/dist/chatcops.min.js"
  data-api-url="/api/chat"
  data-locale="es"
></script>
```

With the script tag build, `data-locale` is all you need when the language has a translation: the chat loads `locales/<language>.js` from next to `chatcops.panel.js`, at the same time as the panel. Only the language part of the code is used, so `pt-BR` loads `pt`. If there's no file for the language, or it fails to load, the chat opens in English and logs a warning. The launcher button reads its label before any of this loads, so set `strings.openChat` in `ChatCops.init` if it should be translated from the start.

### Programmatically

```typescript
ChatCops.init({
  apiUrl: '/api/chat',
  locale: 'es',
  strings: {
    welcomeMessage: '¿En qué puedo ayudarte hoy?',
    greetingWithName: '¡Hola, {name}!',
    inputPlaceholder: 'Escribe un mensaje...',
    sendButton: 'Enviar',
    closeButton: 'Cerrar',
  },
});
```

Your `strings` go on top of the translation, and any string neither of them has stays in English.

### With a bundler

The ESM build doesn't fetch translations itself. Import the one you need from `@chatcops/widget/locales/<code>` and pass it as `strings`, for example `import de from '@chatcops/widget/locales/de'` and then `ChatCops.init({ apiUrl: '/api/chat', locale: 'de', strings: de })`.

The single-file build (`chatcops.full.min.js`) loads nothing else, so pass `strings` there too.

## Available Locales

| Code | Language |
|------|----------|
| `ar` | Arabic |
| `en` | English (default, built in) |
| `de` | German |
| `es` | Spanish |
| `fr` | French |
| `hi` | Hindi |
| `ja` | Japanese |
| `ur` | Urdu |
| `zh` | Chinese (Simplified) |

Any other `locale` uses the English strings, with your `strings` on top. Hindi is loaded as a separate file only when requested. To add a language, see `packages/widget/src/locales/README.md` and [#55](https://github.com/codercops/chatcops/issues/55).

## Locale Strings

`strings` accepts any of these keys:

```typescript
interface LocaleStrings {
  welcomeMessage: string;
  inputPlaceholder: string;
  sendButton: string;
  closeButton: string;
  openChat: string;
  defaultName: string;
  defaultSubtitle: string;
  greetingWithName: string;
  selectPlaceholder: string;
  dismissBubble: string;
  errorGeneric: string;
  errorNetwork: string;
  errorRateLimit: string;
  errorRateLimitWait: string;   // {seconds} is how long to wait
  errorBudget: string;
  errorBudgetDaily: string;
  errorUnavailable: string;
  errorCutOff: string;
  typingIndicator: string;
  poweredBy: string;
  newConversation: string;
  welcomeBubbleDefault: string;
  preChatTitle: string;
  preChatSubtitle: string;
  preChatSubmit: string;
  preChatRequired: string;
  preChatInvalidEmail: string;
  retryButton: string;
  regenerateButton: string;
  suggestionsLabel: string;
}
```

## Server-Side i18n

The server doesn't translate anything itself. When a request has a `locale`, it adds this line to the system prompt:

```text
Reply in the visitor's language. Their browser locale is es.
```

Error messages the visitor sees come from the widget's `strings`:

| Key | Shown when | English |
|---|---|---|
| `errorRateLimit` | Too many messages, and the server didn't say for how long | Too many messages. Please wait a moment. |
| `errorRateLimitWait` | Too many messages, with the server's wait (`{seconds}`) | Too many messages. Please try again in \{seconds\} seconds. |
| `errorBudget` | The conversation used up its budget | This chat has reached its limit. |
| `errorBudgetDaily` | The visitor's or the site's daily budget is used up | The assistant has reached its limit for today. Please try again later. |
| `errorUnavailable` | The server couldn't set up the AI provider (a missing key, say) | The assistant is unavailable right now. Please try again later. |
| `errorCutOff` | The reply stopped before the server said it was done | The reply was cut off. |
| `errorNetwork` | The request failed or timed out | Connection error. Please check your network. |
| `errorGeneric` | Anything else | Something went wrong. Please try again. |

The limit and cut-off messages need a 0.6 server, which sends the reason. With an older server, the widget falls back to `errorRateLimit`, `errorNetwork` and `errorGeneric`. The server config's `i18n` option is deprecated: the server ignores it and logs a warning when it's set, and it will be removed in a later release.
